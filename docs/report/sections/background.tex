\section{Background}\label{sec:background}

\subsection{SpMV formats}
\textbf{CSR} stores row pointers, column indices and values. \emph{CSR-scalar} gives each row one thread, which is
coalescing-unfriendly and serialises long rows; \emph{CSR-vector} gives each row a group of $v$ threads (2--32)
that read the row together~\cite{bell2009spmv}. \textbf{ELL} pads every row to the longest one and stores the
result column-major, so consecutive threads read consecutive words; it wastes memory as soon as row lengths vary.
\textbf{SELL-$C$-$\sigma$} sorts rows by length inside windows of $\sigma$ rows and pads each slice of $C$ rows
only to its own longest row~\cite{kreutzer2014sell}. Vendor libraries add load-balanced CSR kernels; cuSPARSE's
\texttt{CSR\_ALG2} follows the merge-based approach of \citet{merrill2016merge}.

\textbf{ArgCSR}~\cite{heller2012argcsr} packs consecutive rows into \emph{groups} handled by one CUDA block. Within a
group, every row starts with one thread; spare threads are given, one at a time, to the row whose chunk is longest,
and all chunks of a group are padded to the group's chunk size and stored interleaved so that reads coalesce. A group
closes when it would hold more than $\mathtt{desiredChunkSize}\times\mathtt{blockDim}$ nonzeros or more than
\texttt{blockDim} rows. The paper measured 1,600 matrices on a Fermi C2070: ArgCSR beat CPU CSR on 1,168 of them,
was up to ten times faster than the cuSPARSE of 2012 on circuit matrices, and about four times slower on
power-flow matrices.

\subsection{Out-of-core SpGEMM}
Row-wise SpGEMM computes row $i$ of $C$ as $\sum_{k \in A(i,:)} A_{ik} B(k,:)$; the number of multiply-adds of
row $i$ is $f_i = \sum_{k\in A(i,:)} \mathrm{nnz}(B(k,:))$, which also bounds $\mathrm{nnz}(C(i,:))$ from above.
\citet{deveci2018multilevel} run KokkosKernels' \texttt{kkmem} SpGEMM~\cite{deveci2018kkmem} on a KNL and on a P100
connected over NVLink to a POWER8 host. When $A$, $B$ and $C$ exceed fast memory they use two chunked variants:
\emph{chunk1} keeps a row block of $A$ and $C$ resident and streams the row blocks of $B$ (copy volume
$|A| + |C| + |B|\cdot P_{AC}$), and \emph{chunk2} keeps a row block of $B$ resident and streams $A$ and $C$
($|B| + |A|\cdot P_B + |C|\cdot(P_B - 1)$). Columns of $A$ outside the resident rows of $B$ are skipped rather than
split off. Algorithm~4 reserves 75\% of fast memory for the resident and 25\% for the streamed operand, finds row
ranges by binary search, and picks the variant with the smaller copy volume. Their memory study (Table~3) placed
each operand in host-pinned memory in turn: $B$ there costs 7--29\x, while $A$ and $C$ hurt only when they are large.

\subsection{The platform}
Our GPU is an RTX~4050 Laptop (Ada, sm\_89, 6\,GB, 20~SMs, 24\,MB L2) on PCIe~4.0~x8, driven from Ubuntu under WSL2.
Two measurements in \cref{tab:platform} shape the SpGEMM design. Pinned PCIe copies reach \stat{pf-h2d}\,GB/s against
\stat{pf-device-read}\,GB/s for device reads, a ratio of 1:\stat{pf-stream-penalty} (paper 1's NVLink P100 was
about 1:18), and the GPU has a \emph{single} copy engine, so uploads and downloads serialise
(\stat{pf-bidir}\,GB/s together): only copies and computation can overlap. Under WSL2, managed memory is not
migrated: it stays in host RAM and every GPU access crosses PCIe, exactly like pinned zero-copy memory
(\stat{pf-uvm-read} vs \stat{pf-zc-read}\,GB/s); prefetch hints fail and allocations larger than the GPU are
refused. The ``UVM'' baseline of paper~1 is therefore the zero-copy baseline here.
